# 《逆向工程核心原理》第 20 章：内嵌补丁

- 日期：2026-08-26
- 样本/来源：书中 Ap0x `patchme/unpackme #1` 案例；公开学习记录用于核对地址
- 环境：IA-32 PE；计划使用 Ghidra 与 x32dbg
- 进度：等待动态验证

## 问题与分析入口

这章要解决的不是普通的“找到字符串后覆盖文件字节”。目标字符串位于运行时才会解密的区域，而且程序在转入 OEP 前会校验该区域。直接改密文或刚解密后的内存，都可能分别被后续 XOR 覆盖或被完整性校验发现。

先回答三个问题，再设计补丁：

1. 目标字节什么时候才成为明文？
2. 完整性校验什么时候结束？
3. 校验结束到真正使用字符串之间，能否劫持一次执行流？

本例的答案指向同一窗口：校验通过以后、进入 OEP 以前，跳到不受校验的代码洞，在内存里改明文，再跳回 OEP。

## 代码流的静态假设

公开记录给出的 32 位固定地址结构如下；这些地址尚未用本地样本复核：

```text
EP 00401000
  -> 0040109B：B 区 004010F5..00401248 XOR 44h
  -> 004010BD：A 区 00401007..00401085 XOR 07h
                 B 区 004010F5..00401248 XOR 11h
  -> 00401039：累加 B 区校验值
       -> 0040108A：C 区 0040124A..0040127F XOR 17h（IAT）
       -> 返回 00401039，比较校验值
  -> 校验通过后由 00401083 跳到 OEP 0040121E
```

需要特别留意校验循环：`ADD EDX, DWORD PTR [EBX]` 后是 `INC EBX`，所以它读取的是相互重叠的 DWORD，而不是每次前进 4 字节。静态分析时应以真实指针变化为准，不能只看操作数宽度。

目标字符串在 B 区，例如 `0040110A` 和 `00401123`。B 区先后 XOR `44h`、`11h`，随后参与校验；因此补丁代码应在校验后运行。

## PE 映射与代码洞

书中 `.text` 的关键字段为：

```text
ImageBase           = 00400000
VirtualAddress      = 00001000
VirtualSize         = 00000280
PointerToRawData    = 00000400
SizeOfRawData       = 00000400
SectionAlignment    = 00001000
```

原始内容结束于文件偏移 `400h + 280h = 680h`，而该节仍有原始数据到 `7FFh`，所以 `680h..7FFh` 是可持久化到文件的 raw slack。换算公式：

```text
RVA = RawOffset - PointerToRawData + Section.VirtualAddress
VA  = ImageBase + RVA

Raw 680h -> RVA 1280h -> VA 00401280
```

因此示例把补丁例程放在 `00401280`。不能仅凭一串 `00` 就认定它是安全代码洞，还要确认它位于节的原始数据范围、加载后可执行、不被重定位/目录/运行时代码使用，并有足够空间。

## 补丁例程的汇编含义

示例的逻辑骨架是：

```asm
mov ecx, new_string_1_len
mov esi, new_string_1
mov edi, old_string_1
rep movsb

mov ecx, new_string_2_len
mov esi, new_string_2
mov edi, old_string_2
rep movsb

jmp 0040121E
```

`ESI` 是源地址，`EDI` 是目标地址，`ECX` 是复制次数；在方向标志 DF=0 时，`REP MOVSB` 每复制一字节便递增 `ESI/EDI`。长度通常应包含字符串结尾的 `00`。更通用的补丁应考虑 `CLD`，并在中途插入时保存/恢复寄存器与 EFLAGS；书中例子处于启动流程末端，状态要求较宽松。

## 两个相对跳转的计算

`JMP rel32` 编码为 `E9 + 有符号位移`：

```text
disp32 = target - (source + 5)
```

把 `00401083` 的原跳转改为代码洞：

```text
00401280 - 00401088 = 000001F8
机器码：E9 F8 01 00 00
```

代码洞末尾 `004012A2` 返回 OEP：

```text
0040121E - 004012A7 = -89h = FFFFFF77h
机器码：E9 77 FF FF FF
```

最容易漏掉的是：`00401083..00401087` 这条 5 字节 JMP 跨越了 A 区边界，而 XOR 07h 只覆盖到 `00401085`。所以文件中只需预加密前三字节：

```text
运行时需要：E9 F8 01 00 00
文件中写入：EE FF 06 00 00
              ^  ^  ^  这三字节运行时会再 XOR 07h
```

若把后两个 `00` 也 XOR 成 `07`，它们运行时不会被解密，最终位移就会错误。

## Ghidra 与 x32dbg 验证计划

Ghidra：

- 先核对 PE 节表和 EP，不急着相信加密区的反汇编。
- 给三个 XOR 循环、校验函数、OEP 分发点和代码洞加标签。
- 用运行时转储的明文字节建立补丁视图，再重新反汇编 B 区；把“文件密文”和“运行时明文”分开记录。
- 检查代码洞是否落在 `.text` 的 raw slack 内，以及该节是否具有执行权限。

x32dbg：

- 这是 32 位样本，应使用 x32dbg。若实际装载基址不是 `00400000`，全部改用 `module+RVA` 表达。
- 在自修改/被校验区域优先用硬件执行断点，避免软件断点写入 `CC` 后被 XOR 或触发校验。
- 观察 B 区在两轮 XOR 前后的字节，确认字符串首次出现的时刻。
- 在校验比较处记录 EDX 与常量值，并验证跳转到代码洞时校验已经结束。
- 单步执行 `REP MOVSB`，核对 `ECX/ESI/EDI` 和目标内存；最后确认返回 OEP 后程序仍按预期使用新字符串。

## 易错点与现代环境差异

- `VirtualSize`、`SizeOfRawData`、节对齐与文件对齐不能混用；raw slack 必须能从文件映射到目标 RVA。
- 直接修改 B 区会影响校验；过早修改内存还会被下一轮解密覆盖。
- 软件断点本质上写入 `INT3/CC`，对自修改代码和校验区有副作用。
- 示例中的绝对地址 `0040xxxx` 假设固定基址；现代 ASLR 下绝对立即数需要重定位或改成位置无关寻址。模块内 `JMP rel32` 的相对位移本身不受整体基址平移影响。
- x64 没有 `PUSHAD/POPAD`，近跳转还有 ±2 GiB 限制，且覆盖 RIP-relative 指令时必须重写位移，不能机械照搬本章 IA-32 写法。
- 修改磁盘文件会破坏 Authenticode 签名，也可能触发更外层的哈希或反篡改机制。
