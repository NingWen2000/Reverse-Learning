# Feedback Vault 出题记录

## 原始问题

以我现在的能力，给我出一道 CTF 逆向题。

## 当前水平判断

现有练习记录表明，已经能够按黑盒测试、PE 信息判断、字符串交叉引用、核心函数定位、算法还原的顺序分析基础 CrackMe；也接触过 VB6 Runtime、UPX 脱壳、逐字节可逆变换和简单 VM。

目前更值得训练的不是再做一次固定 XOR，而是把多个局部函数还原成完整数据流，并分清“当前轮输入”与“会影响下一轮的状态”。

## 本次题目

本地创建 `05_feedback_vault/player/feedback_vault.exe`，定位为 Windows x64、中等偏入门。选手需要分析：

- 固定长度与 flag 格式检查；
- 非顺序的输入索引；
- 函数指针表产生的间接调用；
- 三段可逆字节变换；
- 每轮更新并传递的 8 位滚动状态。

题目不依赖壳或反调试。难点放在数据流和状态反馈上，预期使用 Ghidra 建立静态公式，再用 x64dbg 观察一两轮的参数、返回值和状态变化。

## 跟做方式调整

学习者明确要求不要一次给出各阶段答案，而要逐操作跟做。后续每轮只安排一个可观察动作：先让学习者报告现象与自己的推断，再决定下一步。先前由出题侧代做的黑盒与 PE 结果不再当作学习者已经掌握的结论，练习 WP 中对应部分已恢复为待填写状态。

学习者随后亲自完成第一次黑盒测试：输入一个 14 字节的普通字符串，观察到程序输出 `Signal rejected.`。目前只记录现象，尚未由学习者提出假设，也没有据此断言失败来自长度、格式或内容中的哪一种检查。

学习者提出第一个静态前假设：输入格式可能是固定的。下一步采用控制变量法，保持总长度为 14，只把输入改成题目声明的 `flag{...}` 外形，以观察输出是否发生变化。

实际测试时先构造了一个带 `flag{...}` 外形但总长度变为 20 的输入；因为两个变量同时改变，这组结果不能隔离格式因素。随后构造总长度为 14 的 `flag{...}` 输入，与第一次形成长度相同、格式不同的对照。两组均观察到 `Signal rejected.`，但尚未替学习者填写这一现象允许或不允许得出的结论。

学习者进入 Ghidra 后通过顶层提示字符串定位到 `FUN_1400015ff`，并询问它是否为 `main`。截图中实际可见该函数负责标题输出、标准输入读取、换行清理、长度与格式检查、核心校验调用、成功/失败输出和退出码返回，因此可判断为源码层面的 `main`，同时应与 PE 入口和 C Runtime 启动函数区分。实际地址与这一判断已写入练习 WP；尚未开始记录核心校验函数内部算法。

随后区分了 `fgets` 的目标缓冲区与返回值：输入内容实际写入栈上的 `local_88`，而 `pcVar4` 接收 `fgets` 返回的指针；成功时两者地址相同，失败时 `pcVar4` 为 `NULL`。这一点用于避免把“保存数据的数组”和“用于检查读取是否成功的指针变量”混为一谈。

对 `memcmp` 的疑问补充到当前笔记：它按指定长度逐字节比较两块内存，返回零表示该范围相等，不依赖 `\0` 终止。当前截图中的调用用于比较输入开头五字节与固定前缀；若后续在 x64dbg 验证，Windows x64 下前三个参数通常分别位于 `RCX`、`RDX`、`R8`。这部分是从静态反编译得到的事实，尚未记录动态寄存器观察值。

学习者已把顶层函数和部分变量重命名，并从 `len == 0x1d` 正确判断输入长度为 29。截图还暴露了一个反编译显示细节：Ghidra 将栈缓冲区显示为 `char input[28]` 与紧随其后的 `local_6c`，而结尾条件中的 `local_6c` 在逻辑上对应第 29 个字符 `input[28]`。结合静态可见的前缀比较，可整理出外层长度、前缀和尾字符约束；核心校验函数仍未展开分析。

首次打开 `FUN_140001550` 后，Ghidra 已把其返回类型显示为 `bool`，并可见输入参数、循环和布尔返回表达式。这里没有把它强行改成 `int`；需要修改返回类型的是此前的顶层 `main`。核心循环尚未解释或重命名，避免把屏幕上刚出现的代码直接替学习者解答。

学习者表示核心函数整体难以理解，分析方式调整为逐层拆解。本轮只处理输入取值：把被用于地址运算的 `input` 视为字节指针，把从零递增到 `0x1d` 的 `lVar4` 识别为轮次。学习者选择将其重命名为更简洁的 `i`，于是第一行整理为 `input[(i * 8 + 5) % 29]`。下一步由学习者自行计算前几轮索引；两个子函数、目标数组和状态反馈仍未解释。

补充 Ghidra 类型修正操作：在 Edit Function 参数表中把 `input` 的 `longlong` 改为 `byte *`，保持 `bool` 返回类型、`__fastcall` 调用约定和自动分配的 `RCX:8` 存储不变。此操作只影响分析元数据，不改变题目二进制。

进一步梳理 Edit Function 窗口：函数名、调用约定、返回值和参数表共同描述函数原型；Storage 显示实际寄存器或栈位置。当前 `AL:1` 对应一字节布尔返回值，`RCX:8` 对应第一个八字节参数。Varargs、Inline、No Return、Custom Storage 和 Call Fixup 都属于会影响语义分析的高级设置，本题当前函数没有证据需要启用；修改数据类型时可完整提交参数细节以保留用户定义的签名。

补充 C 整数字面量知识：索引表达式中的 `5U` 表示类型为 `unsigned int`、数值仍为 5 的常量；`U` 是反编译器恢复出的类型后缀，并非新变量或运算。由于当前循环下标非负，计算索引时可将表达式直接理解为 `(i * 8 + 5) % 29`。

学习者独立计算出前三轮的来源索引分别为 5、13、21，结果正确。由此已经实际确认循环不是自然顺序读取输入；下一步继续计算 `i = 3`，观察模 29 运算如何把索引回绕到有效范围。

学习者继续算出 `i = 3` 时来源索引为 0，因为 `(3 * 8 + 5) % 29 = 29 % 29 = 0`。至此循环第一行已经能解释为按置换顺序读取一个输入字节；下一步才进入紧随其后的 `FUN_1400014ca`，尚未记录该子函数的内部作用。

在确认调用位置、输入参数、29 轮循环和布尔返回值之后，已经有足够证据把 `FUN_140001550` 重命名为 `verify_flag`。这一命名不是仅凭“看起来像校验”猜测，而是由 `main` 的成功/失败分支和函数内部结构共同支持。

进入 `FUN_1400014ca` 后，实际看到一个执行三次的间接调用循环：函数指针来自 `PTR_FUN_140003000` 表，每轮结果重新写回第一个参数。当前 Ghidra 把函数返回类型显示为 `void`，但调用方又把调用结果赋给一个字节变量，两处类型信息矛盾。下一步先解决签名错误，不把 `void` 当作已经确认的事实，也暂不解释三个函数指针的算法。

学习者根据调用方接收变量 `bVar2` 的 `byte` 类型，正确推断 `FUN_1400014ca` 应返回一个字节。下一步只把返回类型从 `void` 改为 `byte`，用反编译结果是否出现 `return param_1` 来检验这一修正；参数语义和函数指针表仍暂不提前命名。

修改后 Ghidra 实际恢复出 `return param_1`，与调用方使用一字节变量接收结果一致，因此返回类型修正得到静态验证。当前继续采用调用点与被调函数相互约束的方法，下一步只映射三个实参与形参，不先进入函数指针表。

首次映射时把第一个和第三个实参交换，原因是两者都是一字节类型，只按类型匹配而忽略了调用表达式的从左到右位置。正确映射为 `param_1 <- bVar1`、`param_2 <- i`、`param_3 <- (byte)uVar3`。这一错误保留下来作为调用分析的提醒：先按参数序号匹配，再用类型和 Windows x64 的 `RCX`、`RDX`、`R8` 寄存器交叉验证。

将间接调用 `(*(code *)(&PTR_FUN_140003000)[j])(...)` 简化为 `pipeline[j](...)`：表地址加索引取得第 `j` 个函数指针，调用结果重新写回 `value`，并在三轮中串联传递。当前只确认“三阶段流水线”这一结构，不提前写出各阶段算法；下一步查看表项地址并只分析第一个目标函数。

实际跳转到 `.data` 段后，截图可确认前两个八字节表项：`0x140003000 -> FUN_14000144e`、`0x140003008 -> FUN_140001486`。两项相差 `0x8`，与 x64 指针宽度一致。第三项没有完整显示，因此保持未知，等待向下滚动到 `0x140003010` 后再记录，不根据源码或预期结构补全。

补充分辨 Listing 右侧的 `XREF[3]`：它表示该位置有三处引用，并不是三个流水线目标函数。函数指针表仍需按 x64 的 8 字节步长分别查看 `0x140003000`、`0x140003008` 和 `0x140003010`。

后两个表项已由新截图确认：`0x140003008 -> FUN_140001486`，`0x140003010 -> FUN_1400014bf`。至此三阶段调用顺序完整为 `FUN_14000144e`、`FUN_140001486`、`FUN_1400014bf`。下一步只打开第一阶段，仍不提前展开后两项。

补充函数指针表概念：表中元素不是普通数值结果，而是可调用函数的入口地址；`pipeline[j](...)` 先读取第 `j` 个地址，再进行间接调用。x64 地址宽度解释了当前表项按 8 字节排列。Ghidra 的 `PTR_FUN_...` 是自动标签，不应误认为源码原始命名。常见用途包括回调、分发表、状态机、VM 和处理流水线。

进一步补全 `j = 0 -> FUN_14000144e` 的证据链：表基址为 `0x140003000`，x64 表项宽度为 8，因此第零项地址仍是 `0x140003000`；该处小端字节 `4e 14 00 40 01 00 00 00` 还原为 `0x14000144e`。对应关系来自索引地址与表项内容，并非按函数地址大小排列。

进一步区分表项位置与内容：`PTR_FUN_140003000` 标签位于 Listing 地址列的 `0x140003000`，这是第一个表项自身的存放地址；该处保存的八字节值才是 `0x14000144e`，对应目标函数。默认标签后缀可以提供线索，但实际 Listing 地址列才是确认依据。

打开第一阶段 `FUN_14000144e` 后，Ghidra 初始显示四字节返回值、两个 `uint` 参数，并生成 `CONCAT31` 表达式。根据流水线调用方的一字节输入、上下文和一字节接收变量，先将这一现象视为签名宽度错误，而不是算法本身复杂。计划把签名统一为 `byte (byte value, ulonglong i, byte context)` 后再读取运算；当前尚未把第一阶段命名或写成最终公式。

学习者完成签名修正后，`CONCAT31` 已实际消失，第一阶段静态公式可整理为 `state ^ value ^ DAT_1400040a0[(i * 3 + 2) % 11]`。其中第三个参数虽然暂时被命名为 `count`，但它来自外层跨轮传递的状态值，后续建议改为 `state`。目前只确认 `DAT_1400040a0` 是按 11 个可能索引读取的字节数据，尚未查看其内容，也尚未动态验证公式；下一步只记录该地址开始的 11 个字节。

学习者已跳转到 `DAT_1400040a0`。当前截图实际显示 `0x1400040a0 = 0x2d`、`0x1400040a1 = 0x91`；其余九字节未出现在截图中，因此保持待确认，不从题目源码或预期结果补全。

后续完整截图已确认 `DAT_1400040a0` 起始的 11 字节依次为 `2d 91 47 b8 53 0e c6 7a 15 e3 69`。由于索引表达式对 11 取模，`0x1400040ab` 及之后显示的零不在第一阶段的可访问索引范围内。当前可使用中性名称 `stage1_table`，但尚不把它定性为完整密钥。

学习者已把第三个参数改名为 `state`，并把数据标签改名为 `stage1_table`。当前反编译仍出现 `(&stage1_table)[...]`，表明 Ghidra 的数据类型仍是单个字节；下一步将已确认的 11 字节范围定义为 `byte[11]`，再观察反编译表达式是否简化。

学习者完成 `byte[11]` 定义后，反编译表达式实际变成 `stage1_table[(i * 3 + 2) % 0xb]`，地址运算中的 `&` 已消失。这一显示变化验证了数组类型修正生效；第一阶段现在可以使用语义名称 `stage1_xor_mix`。尚未进行动态验证，也尚未分析第二阶段。

学习者独立算出 `i = 0` 时的第一阶段表索引为 2，并从已记录的数据表中取到 `0x47`；因此该轮第一阶段表达式是 `state ^ value ^ 0x47`。这仍属于静态代入结果，尚未记录运行时的 `state`、`value` 或返回值。

学习者随后打开第二个表项 `FUN_140001486`。Ghidra 初始误识别为 `void (byte, ulonglong)`，而统一的流水线调用点实际传入三个参数并接收一字节返回值。下一步先修正为 `byte (byte value, ulonglong i, byte state)`，暂不解释屏幕上的 `undefined1[16]`、`SUB161` 和常数乘法表达式。

修正后的截图确认第二阶段返回 `FUN_140001440` 的低字节，第三个统一签名参数 `state` 在此阶段未使用。第二实参含 `i / 5` 以及魔数乘法产生的复杂项；当前教学步骤先令 `q = i / 5`，把魔数项是否等价于 `4q` 保持为待化简问题，不提前记录最终取模公式，也尚未进入辅助函数。

补充 Ghidra 临时值语法：`auVar1` 是 16 字节值，`auVar1._0_8_ = i` 写入低 8 字节，`auVar1._8_8_ = 0` 清零高 8 字节，整体相当于把无符号 64 位 `i` 零扩展为 128 位，用于后续魔数宽乘法。`._offset_size_` 是反编译器的截取表示，不是源码中的结构体成员。

由于学习者仍难以从编译器噪声中把握函数整体，进一步给出分层静态化简：在循环的 `i = 0..28` 范围内，魔数项对应 `4*(i/5)`，所以第二实参为 `i - 5*(i/5) + 1 = i%5 + 1`。第二阶段目前可读成 `FUN_140001440(value, i%5+1)`，而辅助函数的具体操作仍保持未知，等待学习者下一步打开确认；尚无动态参数记录。

补充魔数项的证据：`ZEXT816` 将除法魔数扩成 128 位，宽乘法后 `SUB161(...,8)` 取乘积第 64～71 位，`&0xfc` 清低两位。利用 `high64(i*0xcccccccccccccccd)>>2 = floor(i/5)`，且本题 `i<=28` 不会因只取该字节而丢失商的信息，可得该项为 `4*floor(i/5)`。可用区间输出 0、4、8……进行静态交叉检查；仍未记录调试器实测值。

进一步记录魔数来源：`0xcccccccccccccccd = ceil(2^66/5) = (2^66+1)/5`。令 `P=i*M`，则 `high64(P)>>2 = P>>66 = floor(i*M/2^66)`；代入 M 后为 `floor(i/5 + i/(5*2^66))`，在无符号 64 位范围内等于 `floor(i/5)`。该推导解释了编译器如何以宽乘和移位替代常数除法。

学习者追问的是实战中如何想到这一点，而非公式证明。记录更合适的方法：把“大魔数 + 宽乘 + 取高位 + 移位/掩码”识别为常数除法候选；利用同一表达式里直接出现的 `i/5` 提供上下文；在 `i=0..28` 上用边界试值观察 `0,4,8,...`；必要时用 `2^(64+2)/M≈5` 反推除数。无需要求初学者现场推导魔数生成公式。

学习者继续打开第二阶段辅助函数 `FUN_140001440`。初始签名被识别为 `undefined8 (ulonglong, byte)`，并出现 `CONCAT71`；调用方与函数内部实际只关心第一参数和返回值的低字节。下一步先修正为 `byte (byte value, byte shift)`，将左右移位加按位或仅作为循环移位候选，等待新反编译结果确认。
